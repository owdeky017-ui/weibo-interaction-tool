从 0 到 1

八步走到今天，每一步都是因为上一版不够用

没有现成工具，没有教程，也没有一开始就设计好的架构。 下面八步是实际发生的顺序 —— 包括「同一个问题连换三遍方案」的部分。

  1. 2026-08-15 · 第 0 天

    urllib 直连移动端接口

    想统计一个微博博主的说话习惯，找不到现成工具，于是自己写。 用 urllib.request 加 http.cookiejar 伪装成移动端浏览器， 请求 m.weibo.cn 的分页接口。 问题：首页能拿到，翻页不稳，cookie 维护很别扭。

  2. 2026-08-15 · 同一天

    换 Selenium 驱动系统 Edge

    接口翻页拿不全，那就让浏览器自己去点「加载更多」—— 用 Selenium 启动系统已装的 Edge，顺带复用真实登录态。 问题：等待时机只能靠 sleep 猜，日志里刷满页面自身的 JS 报错。

  3. 2026-08-15 · 同一天

    再换 Playwright：把翻页逻辑注入页面上下文

    关键转变 —— 不再从 Python 侧猜页面状态，而是用 page.evaluate 把翻页逻辑注入页面里执行，让 JS 自己循环请求、自己去重、自己判终止， 最后把累积结果一次性交回 Python。 结果：稳定拿到 1461 条微博。

  4. 2026-08-15 · 同一天

    analyze.py：从「抓到」到「看懂」

    清洗话题标签 / @ / URL 之后，统计表情符号、语气词、标点习惯、自称、句长分布、 发博时间分布，再提取代表性台词。 这一天的收获不是脚本，而是意识到：抓取只是手段，真问题是「怎么量化一个人的表达习惯」。

  5. 之后

    从「一个人」扩展到「两个人」

    需求变了：不再只看一个人发了什么，而是看两个人之间发生过什么 —— 转发、评论、评论回复、点赞。这一步把项目从「一次性爬虫脚本」推成「有状态的应用」： 必须处理增量扫描、断点续传、跨次去重、请求限速、风控退避。

  6. 之后

    做成桌面工具，而不是命令行脚本

    要给不用命令行的人用，就得有界面。改成 tkinter GUI + 扫码登录 + 一键导出 Excel / CSV / HTML， 再用 PyInstaller 打包成绿色免安装的分发版。

  7. 本月

    手上只剩打包产物，于是逆向还原

    要改进它，先得知道它到底怎么写的。Python 3.13 没有可用的反编译器 （uncompyle6 止于 3.8、decompyle3 止于 3.9），所以只能从 PYZ 里读字节码、 常量表和 docstring，手工重建逻辑。

  8. 本月

    建独立改造工程，做工程化收口

    随后找到原始源码，据此新建独立工程：六项性能改造、登录态加密、 三层打包验证、约束收敛成编译期常量，以及一整套自动化测试。 原分发目录全程未改动（exe 的 MD5 前后一致）。

第 7 步展开：从 PYZ 里把结构捞出来

1 解析 PYZ 归档

onedir 的 exe 内嵌一个 PYZ 归档。定位 b'PYZ\x00' 魔数，读 offset+8 的 int32 得到 TOC 偏移，marshal.loads 解析出条目表， 再对每条 zlib.decompress + marshal.loads，就拿到了 code 对象。

这一层后来还派上了别的用场：build.py 的自检就是靠同一套方法 直接读 exe 内嵌 PYZ 里 build_mode 的编译常量， 来确认 A_MODE 真的写进了编译产物。

2 还原出 9 个模块

最终确认的结构：gui_app（GUI）/ main（CLI）/ analyzer（编排·去重·断点）/ client（HTTP·限速·风控）/ fetchers（解析）/ exporter（导出）/ login（扫码）/ config / utils， 以及各模块的函数签名、常量值与用到的微博 API 端点。

顺带发现的两个「看起来是 bug、其实不是」的点

① fetch_reposts / fetch_attitudes 的 start_ts 参数确实是死参数（函数体从未使用），但按时间剪枝在这个场景永不触发 —— 微博的创建时间必然 ≥ 扫描窗口起点，互动时间又必然 ≥ 微博创建时间。 真正省请求的是「命中即停」。
② exporter 里对正文的 120 字截断是死代码：截断后的数据只用于汇总表， Excel/CSV 实际写的是完整记录。

功能

它做什么

提取两个微博用户之间的双向互动记录，导出成可检索的单文件 HTML 日志 （可选 Excel / CSV）。所有互动类型都支持 A→B 与 B→A 两个方向。

↻转发

谁转发了谁的哪条微博，含转发语。

💬评论

对微博的评论，含折叠评论的「热度 + 时间」双排序覆盖。

↩评论回复

评论楼中楼的连续回复，标注「回复的是哪条评论」。

♥点赞

微博网页版无公开点赞接口，改用移动端接口尽力尝试。

增量刷新

同一对用户再次抓取时，只扫新增微博 + 重扫最近 3 天的旧微博 （旧微博也可能被对方新评论 / 新点赞）。

断点续传

中断、暂停、手动结束后都可从断点继续，不会重复扫描； 抓取中途登录失效会自动弹新二维码。

风控自适应

触发风控自动等待 180 秒后继续；点赞接口不可用时自动暂停， 每 50 条微博重试一次。

架构

模块与数据流

两条入口（GUI / CLI）共用同一套核心；analyzer 是唯一的编排层， 网络、存储、导出都通过它串联，因此性能优化可以集中在一处做。

并发度怎么定

并发只影响「同一时刻几个请求在途」，不改变请求总数与平均 QPS —— 所以不会让风控更容易触发。

速度请求间隔并发线程
慢（最稳）1.2 s1（严格串行）
中0.6 s2
快（易风控）0.25 s3

并发带来的两个必须处理的细节

  • Session 不是线程安全的 —— requests.Session 的 cookie jar 有共享状态。用 threading.local 给每个 worker 一份独立 Session （慢速单线程时仍复用同一个，行为与原来完全一致）。
  • 风控异常必须由调用线程上抛 —— 否则外层「等 180 秒后重试」的语义会丢。 worker 里捕获 RiskControlError 收集起来，回到调用线程统一抛。

约束落地

产品约束做成编译期常量，不是散落各处的 if

「用户A 只能是当前扫码登录的账号」是产品的硬约束。它没有散落在业务代码里， 而是收敛成一个编译期常量：build_mode.A_MODE， 打包脚本在编译前把它写进 build_mode.py。 约束因此只有一个判定点，改需求时不会漏掉某个分支。

锁定 用户A = 登录账号

输入框只读、登录后自动填入，只需要填用户B。 查「你和某个人」的互动时更省事，也从机制上杜绝了填错自己。

可测试性 常量带来的另一个好处

测试可以在同一进程里替换 build_mode 再重新导入模块， 让这个常量的各个取值都被跑到 —— 而且是真实构建 GUI 后读控件状态， 不是断言一个常量。

分支点本版行为
GUI 用户区标题2. 选择要对比的用户
用户A 输入框只读，登录后自动填入
配置记忆只记忆 B（A 永远取登录账号）
开始前校验只校验 B，且 B 不能是登录账号本人
命令行 --u1隐藏，传了会明确报错

最后一项不是洁癖，是数据正确性问题

「用户A = 登录账号」这个约束下，如果重新扫码时换了账号，A 就变了 —— 断点里的历史记录和 scanned_mids 都不再对应新的用户对， 继续跑会把两个人的记录混在一起。所以必须中止而不是续传。

工程化

三层验证：每一层回答一个不同的问题

打包类的项目最容易出的错是「以为打了，其实打的是上次的产物」。 所以验证按「源码行为 / 产物结构 / 冻结运行时」拆成三层。

1 源码行为

smoke_test.py · 119 项断言

  • 导出格式：sheet 顺序、表头、长文本不截断、空记录分支
  • 剪枝正确性：命中页数、目标不存在时不提前退出
  • 断点：增量追加、主键去重、旧 JSON 迁移、文件损坏容错
  • 令牌桶：突发额度、平均速率不超标
  • 并发：耗时、异常语义
  • 模式分支：真实构建 GUI 后读控件状态，而不是断言常量
  • 登录态加密：往返、篡改检测、明文自动升级

另有 pytest 用例集（tests/，207 项）覆盖 client / analyzer / exporter / checkpoint / login / fetchers / utils 的边界条件，CI 上跑覆盖率。

2 产物结构

build.py 内建自检

  • 目录结构完整
  • 直接读 exe 内嵌 PYZ 里 build_mode 的编译常量， 确认等于目标模式
  • 产出 exe 的 sha256 与预期一致
  • data/ 不含任何运行时数据（不会把登录态打进分发包）

第二项比「比对时间戳」强得多 —— 前者只能推断，这个是直接读编译产物。

踩过的坑

六件「写的时候没想到、跑起来才炸」的事

功能列表谁都能列，真正说明「有没有亲手跑过」的是这些细节。 每一条都改过代码，不是事后总结。

1 打包脚本第二次运行必然失败

PyInstaller 在 --noconfirm 下会先自己删掉已存在的 dist/<name>。文件上千个时这一步会被安全软件拦下， 实测报 SAFE_DELETE_BULK_CONFIRM_REQUIRED。

解法不是去找一个「确认删除」的开关，而是把删除动作本身去掉： 每次输出到全新的 dist_<时间戳> 目录，组装完再移动。 --clean 也从默认改为可选 —— 清缓存只会拖慢下次打包。

2 冻结环境里中文输出全是乱码

自检脚本编成 exe 后输出乱码。原因不在 PyInstaller：冻结运行时下 stdout 走系统区域编码（中文 Windows 是 GBK），而父进程按 UTF-8 读。

修法是脚本启动时强制 sys.stdout.reconfigure(encoding="utf-8")。 这个坑只在「父进程读子进程 stdout」时出现，本地直接跑完全看不到。

3 _internal/ 里找不到 urllib3 ≠ 没打进去

检查打包结果时没找到 urllib3、idna、 PIL/ImageTk.py，一度判断为依赖缺失。

实际上纯 Python 模块被编译进 exe 内嵌的 PYZ（本例 729 个模块）， 只有带 .pyd 的包才会以目录形式落在 _internal/。要确认得展开 PYZ 去数模块，不能看目录 —— 顺带才确认了 pandas / numpy 确实没被混进去。

4 DPAPI 的完整性保护有边界

加密改造后做逐字节篡改测试：payload 区 274 字节全部被检测到。 但 DPAPI blob 的字节 4–19 不受完整性保护 —— 那是 dwFlags 加 16 字节 description，属 API 已知行为。

不实测一次，很容易误以为「整块 blob 都不可篡改」， 从而写出错误的威胁模型。

5 「能启动」不等于「能运行」

最初的验证只做到「exe 起来后存活 12 秒不崩」。 这只能证明启动路径没炸，证明不了运行时可用： 证书链缺 cacert.pem、sqlite3.dll 版本不对、 PIL.ImageTk 找不到 _imaging —— 这三类都要真跑一次才暴露。

这就是「三层验证」里第 3 层存在的唯一理由。

6 CI 从没真正跑过，第一次跑就红了两次

仓库初始化时漏提交了 models.py、tests/、 .github/workflows/ci.yml 三块 —— clone 下来既没有 CI 定义，也跑不了 pytest。 补齐后推上去，第一次真正执行就暴露 ruff check . 在测试脚本上的 87 项问题。

更隐蔽的是第二个：mypy 在本机 Windows 上过， 在 CI 的 Linux runner 上不过 —— ctypes.windll 与 os.startfile 在 Linux 的类型桩里不存在， sys.platform 判断之后的代码还会被判成 unreachable。 mypy 默认按运行它的主机选类型桩，解法是显式钉住目标平台。

教训很直白：本地跑得通 ≠ 仓库是完好的。 判断依据应该是「新机器 clone 下来能不能跑」。

安全与边界

两件我做了和一件我没做的事

已做 登录态加密存储

原实现把含 SUB/SUBP 的登录态明文写在 data/cookies.json —— 任何能读到这个文件的人都能直接冒用账号。

  • 改用 Windows DPAPI 加密，附加熵绑定到本程序
  • 密文绑定当前 Windows 用户与机器，换机器解不开
  • 旧的明文文件会被自动识别并就地升级，用户无感
  • 用 CRYPTPROTECT_UI_FORBIDDEN，打包成 GUI 后不会弹系统对话框
  • DPAPI 不可用时退回明文，保证程序不会因加密而不可用

实测：payload 区 274 字节逐字节篡改全部被检测到。 （DPAPI blob 的 header 4~19 字节不受完整性保护，属已知行为，不涉及密文内容。）

未做 没有做成在线服务

把「扫码登录 + 抓取」搬成公开网站技术上可行，但我判断不应该做，三条理由：

  • 它必须让访客交出微博登录态。服务器要保存每个访客的 cookie， 一旦被攻破就是批量账号失窃 —— 形态上与钓鱼站没有区别。
  • 违反微博用户协议。微博禁止自动化抓取，公开站点规模化运行 必然被风控与 IP 封禁，且把违规行为放在了公网可查的位置。
  • 抓到的是他人的互动数据。公开提供「查某人和某人的互动」本身就是隐私问题。

所以这个项目保持为本地桌面工具：数据不出本机， 登录态加密存在本机，抓取速率受控且总量有限。

工程细节

几个值得单独说的决定

为什么断点要用 SQLite 而不是 JSON

原实现每次保存都要「读全量 → 按 _key 在内存里合并 → 写全量」， 复杂度 O(记录数)；实测单个断点文件已经涨到 665 KB，而且靠 os.replace 做原子替换。改成 SQLite 后去重交给主键、 只写新增、断电也不会把整份断点写坏。

断点保存失败为什么不该静默

原实现是 except Exception: pass。断点写失败时用户毫无感知， 以为存了其实没存，下次「继续」会从更早的位置重扫甚至丢进度。 改成显式提示，但不让提示本身的异常掩盖原始错误。

去依赖时发现的死代码

原实现对正文做了 120 字截断。但截断后的数据只喂给汇总表（不涉及正文）， Excel / CSV 实际写进去的仍是完整记录 —— 这段截断从来没生效过。

重构时很容易顺手「保持原行为」把死代码一并抄过来。判断依据应该是 实际产物里是什么，而不是源码里写了什么。

剪枝的前提是「能证明不影响覆盖度」

评论双排序剪枝只在三种情况下生效：时间序拿到的条数等于接口声明的 total_number。如果被页数上限截断、条数少于声明值、 或者接口压根没返回这个字段，一律退回跑双排序 —— 宁可多花请求，也不能漏数据。

已知限制

  • 点赞数据可能不完整：微博网页版没有公开的点赞列表接口， 改用移动端接口尽力尝试，接口不可用时自动暂停并在每 50 条微博后重试。
  • 评论可能不全：评论区存在折叠与拉黑隐藏机制， 被博主拉黑的用户其评论对公众完全隐藏，公开接口无法获取。
  • 只能抓公开内容：对方的隐私设置、已删除内容、仅粉丝可见的微博都拿不到。
